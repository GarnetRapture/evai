# EverTalk 페르소나·인연·맥락 구현 추적

이 문서는 EverTalk 프로덕션 채팅의 구현 기준과 검증 결과를 기록한다. 코드가 없는 설계나 실행하지 않은 시험은 완료로 표시하지 않는다.

## 최종 서비스 계약

1. 대화가 전혀 없을 때 `data/personas`의 정령 데이터가 유일한 시작 정체성이다.
2. 정령 데이터는 외부 참고자료가 아니라 모델이 맡은 실제 정령의 삶·성격·과거 발화다.
3. 일반적인 한국어 말투 등급이나 고정 어미로 성격을 다시 정의하지 않는다.
4. 사용자의 대화가 쌓이면 화법·관계·관심·반응 방향이 실제 공유 기억을 통해 점진적으로 달라진다.
   이 변화의 권한은 사용자의 명시적 요청과 반복 확인된 선호에 있다. 정령의 이전 생성문은 사건·감정·약속으로 기억하지만, 그 문장 하나가 성격·거리감·관계 규칙을 스스로 다시 쓰게 두지 않는다.
5. 정령의 신원은 유지되지만 시작 페르소나 문장을 기계적으로 반복하거나 영구 고정하지 않는다.
6. 매 응답은 단발 호출이 아니라 정령별 인연과 룸별 시간순 히스토리의 다음 턴이다.
7. 오래된 대화는 버리지 않고 룸·정령별 digest로 압축하며, 최근 연속 대화와 함께 다음 턴에 전달한다.
8. 설정 언어가 한국어면 한국어, 영어면 영어, 중국어면 간체 중국어로만 응답하고 이모지를 제거한다.
9. Chrome Prompt API가 허용하는 최상위 입력인 첫 `system` initial prompt에 정령 페르소나를 넣고, 원본 반응쌍은 뒤이은 `user/assistant` few-shot으로 분리한다.
10. IndexedDB가 기본 저장소다. C++26 네이티브 저장소·추론 호스트는 사용자가 선택하는 확장이고 웹 사용을 강제하지 않는다.
11. `<think>`는 화면에 노출하되 메시지 재주입, episodic 기억, digest, semantic 기억에는 넣지 않는다.
12. 다음 턴의 `<think>`는 일반 업무 판단이 아니라 초기 정령상, 최근 대화, 사용자가 강조한 기억, 누적된 관계 변화 사이의 차이를 확인하는 정령의 현재 감정·반응 과정이다.
13. 실제 대화 이력이 있는 정령은 일정 시간 사용자의 새 입력이 없으면 낮은 확률로 기존 맥락의 궁금증을 이어 먼저 말할 수 있다. 이 발화는 일반 정령 응답으로 저장하고, 확인 전까지 정령별·전체 알림 수로 표시한다.
14. 사용자의 최신 입력은 기본적으로 해결할 질문이나 업무 요청이 아니라 두 사람이 이어가는 대화의 다음 순간이다. 직접적인 의문문만 관계 안에서 자연스럽게 답하며, 응답 형식을 일반 질의응답 해설로 바꾸지 않는다.

## `data/personas` 전수 분석

2026-09-12에 `data/personas/*.json` 99개를 JSON 파싱해 원본 필드와 대화 배열을 계측했다.

|---|---:|---|---|
| 기본 식별·프로필·성격 | 99개 | 대화가 없을 때의 시작 정체성·취향·배경 | 항상 시스템 프롬프트의 최상단 기준으로 사용 |

### 대화 자료의 구조적 특징

- 전체 `story + evertalk`는 정령 발화 14,656줄, 상대 발화 7,294줄이다.
- 실제 `구원자 -> 정령의 연속 응답`으로 묶을 수 있는 반응 예시는 2,799개이며 80개 정령에 존재한다.
- 동일 선택지/발화의 연속 중복이 3,807건이다. 원본을 수정하지 않고 파서 단계에서만 중복 제거해야 토큰을 낭비하지 않는다.
- 타 정령이 중간에 등장하는 파일이 7개다. 이를 구원자 발화로 오분류하면 잘못된 반응 학습이 되므로 화자 식별이 필요하다.
- 17개 정령은 `speech_patterns`와 대화 배열이 모두 비어 있다. 이 경우 임의 말투를 생성하지 않고 `personality.description`과 `greeting`만 시작 음성 근거로 사용한다.
- 4개 정령(Canney, Casper, Irene, Pixie)은 설명 현지화도 비어 있다. 빈 필드는 `-`로 유지하고 모델이 추측해 채우게 하지 않는다.

### 소연 데이터 검증

- 프로필, 성격 설명, 인사, `speech_patterns` 50줄, `evertalk` 255줄이 존재한다.
- 중복 선택지를 제거한 뒤 `구원자 -> 소연` 반응 묶음 35개를 만들 수 있다.
- 예를 들어 `잘 하는 것 같은데?` 뒤의 `헤헤…그래?`, `앞으로 잘 부탁행`, 실수에 당황하는 연속 반응은 단독 어미 통계가 아니라 칭찬을 받았을 때의 감정·말투·행동 방향을 함께 보여준다.
- 따라서 소연의 초기 주입은 프로필·성격·인사 + 정령 단독 발화 표본 + 실제 반응 대화쌍으로 구성해야 한다. 이후 실제 사용자와 쌓인 기록은 별도 관계 변수로 이 시작값을 점진적으로 변화시킨다.

### 가넷 회귀 검증

- 제보 화면은 이름·캐럿 취향은 참조했지만, 실제 가넷 반응쌍을 시스템 문자열 속 설명으로만 취급해 중립적인 존댓말 리듬으로 평준화된 상태였다.
- 가넷 원본의 `구원자님`, 캐럿, 강한 친밀감과 반복·기호 표현이 조립 프롬프트와 현재 주제 검색 결과에 존재하는지 별도로 검사한다.
- 원본 `<example>`을 파싱해 Chrome `initialPrompts` 및 GGUF/LiteRT-LM 메시지의 실제 `user/assistant` 역할쌍으로 승격했다. 시스템 본문에서는 같은 예시 태그를 제거해 토큰을 이중 소비하지 않는다.
- 2026-09-13 실제 `chatService.sendMessage()` 종단 검증에서 `캐럿 꾸미기`보다 `좋아한다`, `기억해` 같은 일반 표현이 더 높은 관련도 점수를 받는 결함을 재현했다. 검색 점수를 정확히 일치한 희소 주제어(IDF)에 우선 배정하고 문자 n-gram은 보조 점수로 낮춰, 첫 동적 예시가 실제 `캐럿` 반응쌍인지 검사하도록 교정했다.
- 모델의 실제 생성 품질은 브라우저 내장 모델 상태에 의존하므로 자동 시험은 “가넷 전용 데이터가 다른 정령과 섞이지 않고 실제 역할 메시지로 전달되는 계약”까지 담당하고, 최종 발화 평가는 실제 브라우저에서 수행한다.

### 토큰 예산 결론

모든 21,936줄을 상시 시스템 프롬프트에 넣으면 Chrome이 실제로 제공한 컨텍스트 창과 최근 대화 공간을 소진한다. 특정 파라미터 수를 가정하지 않고 `LanguageModel.contextWindow/contextUsage` 실측값을 사용하며, 원본 전체는 파싱 가능한 학습 코퍼스로 유지하고 다음 세 층으로 사용한다.

1. 항상 유지: 프로필·시작 성격·인사와 분산 표집한 실제 정령 발화.
2. 시작 반응 학습: 전체 대화에서 중복을 제거하고 분산 표집한 소수의 실제 `구원자 -> 정령` 대화쌍.
3. 현재 턴 보강: 사용자 최신 발화와 관련도가 높은 실제 대화쌍만 검색해 현재 턴 훅에 추가.

이 구조는 중요한 캐릭터 정의를 상시 유지하되 예시 대화는 토큰 여유에 맞춰 관리하는 역할대화 서비스의 일반적인 컨텍스트 분리 방식과 맞고, Nano의 최근 히스토리 공간도 보존한다.

## 확인된 현재 호출 흐름

```text
data/personas/*.json
  -> persona/slice.ts: 설정 언어 데이터 선택
  -> persona/speech.ts: 실제 정령 발화 표본 선택
  -> persona/prompt.ts: 영문 시스템 지침 + 현지화된 정령 데이터
  -> persona/service.ts: 정령 프롬프트 조립
  -> chat/service.ts: 최근 히스토리·digest·장기 기억 조립
  -> llm/engine.ts
       -> Chrome: initialPrompts = system + 해당 정령 few-shot 역할쌍
       -> GGUF: messages = system + 해당 정령 few-shot 역할쌍 + 실제 히스토리
       -> LiteRT-LM: systemPrompt + 해당 정령 few-shot 역할쌍 + 실제 히스토리
```

## 저장·인연 흐름

```text
사용자 메시지 저장
  -> IndexedDB 권위 저장 + 선택 시 EXE 옆 SQLite 미러
  -> 명시적 기억/취향 감지
  -> 룸별 최근 연속 히스토리 조회
  -> 관련 episodic 기억 검색
  -> 정령 응답 생성
  -> 응답 + episodic 기억 원자 저장
  -> 관심 주제 누적
  -> 일정량마다 semantic 관계 기억 통합
  -> 오래된 룸 대화는 digest로 압축
  -> 메시지·기억 누적으로 인연 경험치와 레벨 상승
```

### 선제 대화·알림 흐름

```text
앱 실행 중 5분 주기 검사
  -> 실제 사용자 발화가 존재하는 정령·룸만 후보화
  -> 최근 활동 20분 유휴 + 정령별 시도 90분 쿨다운 + 미확인 3개 상한
  -> 후보 하나를 선택하고 28% 확률 통과
  -> 정령 기본 페르소나 + 관계 상태 + digest + 최근 실제 대화 + 관련 episodic 기억 조립
  -> 저장하지 않는 현재 시점 트리거로 미해결 약속·감정·궁금증 중 하나를 생성
  -> 정령의 선제 assistant 발화만 IndexedDB에 저장하고 선택 시 SQLite에도 동일 본문 미러
  -> 좌측 정령별 배지와 최상단 통합 알림에 같은 미확인 건수 표시
  -> 사용자가 해당 정령을 열거나 답장하면 그 정령의 선제 발화만 읽음 처리
```

초기 기본 정령을 앱이 자동 선택하는 행위는 사용자 확인으로 간주하지 않으므로 알림을 지우지 않는다. 모델을 깨우기 위한 내부 트리거는 실제 사용자 메시지나 episodic 기억으로 저장하지 않는다.

## 조사 근거

- [Chrome Prompt API](https://developer.chrome.com/docs/ai/prompt-api): 시스템 프롬프트는 `initialPrompts`의 첫 `system` 메시지로 세션 생성 때 제공한다. `contextWindow`, `contextUsage`, `measureContextUsage()`로 실제 컨텍스트 예산을 계산한다. 정령 대화 세션은 공식 `balanced`, digest·semantic 압축 세션은 `predictable` sampling mode를 사용한다. 웹 Prompt API에는 요청별 최대 출력 토큰이나 GPU 강제 속성이 없으므로 존재하지 않는 옵션을 만들지 않고, 실제 컨텍스트 창에서 응답 공간을 제외한 나머지를 최근 연속 히스토리에 사용한다. `availability()`에도 생성과 동일한 언어·sampling 조건을 전달한다.
- [Chromium 성능 등급 구현](https://chromium.googlesource.com/chromium/src/+/HEAD/components/optimization_guide/core/model_execution/performance_class.cc): GPU 가능 여부와 성능 등급을 Chrome이 측정하며, 저성능 GPU가 아니면 `HIGHEST_QUALITY`, 그다음 `FASTEST_INFERENCE`, 마지막으로 CPU 힌트를 내부 우선순위로 선택한다. 일반 웹 페이지는 이 내부 백엔드 선택을 강제하지 않는다.
- [Prompt API 표준 초안](https://github.com/webmachinelearning/prompt-api/blob/main/index.bs): 컨텍스트 창 크기는 사용자 에이전트 구현값이고 공개 생성 옵션에 `maxTokens`나 GPU 선택은 없다. 따라서 화면에서 확인된 `nano_v3_gpu_high_tier_model` 약 4,072 MiB를 실제 활성 자산으로 기록하되, 모델 파라미터 수나 컨텍스트 상한을 파일 크기에서 추정하지 않는다.
- [`chrome://flags` Chromium 소스](https://chromium.googlesource.com/chromium/src/+/main/chrome/browser/about_flags.cc): `#prompt-api-for-gemini-nano`는 Prompt API 기능 활성화용이다. 과거 개발 환경의 `#optimization-guide-on-device-model=Enabled BypassPerfRequirement`는 하드웨어 검사 우회용이며 페르소나나 시스템 메시지를 바꾸지 않는다. 모델 설치 상태는 `chrome://on-device-internals`에서 확인한다.
- [Prompt API 제안](https://github.com/webmachinelearning/prompt-api): 첫 시스템 메시지와 `initialPrompts`는 오버플로 때 제거되지 않는다. 공개 `LanguageModelCreateOptions`는 언어·입출력·도구·sampling·initial prompt만 정의하며 브라우저 내부 기본 지침을 끄는 옵션은 없다.
- 결론: 일반 웹 JS가 `chrome://flags`를 변경하거나 브라우저 내부 정렬 프롬프트를 제거할 수 있다고 가정하지 않는다. 실제 제어면은 첫 `system` 정령 프롬프트, 실제 대화 예시, assistant `<think>` prefix, 설정 언어 선언, 결과 이탈 감지 후 1회 재생성이다.
- [Hugging Face chat template 문서](https://huggingface.co/docs/transformers/main/chat_templating): GGUF 등 직접 호스팅 모델은 모델이 학습한 chat template의 역할 토큰을 보존해야 한다. Chrome 옵션과 달리 직접 런타임에서는 template 및 assistant prefill을 제어할 수 있다.
- [llama.cpp assistant prefill](https://github.com/ggml-org/llama.cpp/blob/master/common/common.h): 마지막 assistant 메시지를 응답 prefix로 이어 쓰는 기능이 존재한다. GGUF 경로는 이를 이용해 `<think>`부터 생성하도록 설정했다.
- SillyTavern: 캐릭터 정의, 예시 대화, 채팅 히스토리, 동적 월드 정보와 메모리를 서로 다른 컨텍스트 층으로 관리하고 토큰 예산을 둔다.
- RisuAI: 최근 대화의 활성 키에 맞는 lore만 삽입해 불필요한 토큰을 줄인다.
- RoleLLM 및 역할극 메모리 연구: 프로필 충실도와 장기 대화 기억은 별도 평가 대상이며, 관련 기억을 대화 맥락에 맞춰 회수하는 구조가 지속적인 캐릭터성을 높인다.
